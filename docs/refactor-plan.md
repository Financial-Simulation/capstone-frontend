# 프론트 리팩터링 · v1.7 반영 계획

> 담당: 이윤제 · 시작 11/8 · 기준 문서: 구현 명세서 v1.7(조민석 11/1) 9.3·13장, `capstone-backend/API_CHANGES_v1.7.md`
> 단계마다 "설명 → 코드 변경 → 실행·테스트 → 커밋" 한 바퀴로 진행하고, 끝나면 아래 체크를 채운다. 팀 저장소에는 몇 단계씩 묶어 PR로 올린다 (첫 PR은 1단계 뒤).

## 왜 하나

1. **v1.7 세금 모듈 반영**: 연말정산 환급, 주택청약 · 연금저축, 월세 세액공제, 상품별 배분, 배분 자동 추천, 리포트.
   지금은 백엔드 합본의 빌드 파일(`static/index.html`)에 `frontend-addon/tax-addon.js`(약 600줄)를 끼워 넣은 임시 방식이다.
   요청을 중간에 가로채 칸을 끼우고, 화면에 블록을 덧붙이고, 값은 `taxAddon.v1`에 따로 저장한다 → 앱 소스 컴포넌트로 옮긴다.
2. **하드코딩 걷어내기**
   - 결과 화면 숫자가 목업(v1.6 정답 파일 8개 입력)에서 나온다. 백엔드에 실제 계산 API가 생겼다.
   - 화면 문구에 제도 숫자가 박혀 있다('연 3.03%', '월 50만 원까지', '총급여 7,500만 원 초과' 등).
     v1.7에서 정부 지원금 기준이 총급여 6,000만 원으로 바뀌어 이미 틀린 문장이 생겼다.
   - 목업 핸들러와 입력 규칙(`rules.ts`)이 서버 규칙을 손으로 베낀 사본이다.
   - tax-addon 안에 세율표로 '내는 세금'을 화면에서 계산하는 부분이 있다 (명세서 9.3-3: 서버 값으로 바꾸길 권장).
3. **팀 공유**: 소스가 개인 컴퓨터에만 있고 git 기록이 없었다 → 팀 저장소에서 PR로 관리한다.

## v1.7에서 바뀐 API (요약)

| 구분 | 내용 |
| --- | --- |
| 새 입력 (모두 선택) | `income.annualGrossSalary` 세전 연봉 · `expenses.monthlyRent` 그중 월세 · `person.homelessHouseholder` 무주택 세대주 · `savingPlan.policyMonthly / housingMonthly / pensionMonthly` 상품별 배분 |
| 응답 추가 | `/simulate`의 `tax`(환급 · 낸 이자소득세 · 추징 · 연금 기타소득세 · 순이득 · 청약·연금 해지 확률 · 실제 배분), `/compare` 줄마다 `medianAtGoal` · `taxNetBenefit` · `allocation` |
| 새 API | `POST /allocations/recommend`(가장 좋은 배분), `POST /reports`(리포트 데이터), `POST /robust` + `GET /robust/{jobId}`(가능성 범위, 비동기 작업) |
| 새 오류 키 | `income.grossConsistentWithNet`(세전 연봉 × 1.1 ≥ 실수령 × 12) · `expenses.rentWithinFixed`(월세 ≤ 고정지출) |
| 그대로 | 새 칸이 없으면 v1.6과 같은 결과 (S1 58.0%) |
